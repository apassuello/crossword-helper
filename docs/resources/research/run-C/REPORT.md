Research run, 2026-09-02. Scope: American-style crossword **construction**. Solving work appears only where a technique transfers, and the transfer is stated each time.

## Methodology and how to read this document

Sources are numbered `[1]`–`[52]` in the SOURCES table at the end; findings cite those numbers. Retrieval status means exactly this: **FETCHED** — the raw bytes were saved to a file under `corpus/` and that file was read; **ABSTRACT** — only an abstract or landing page was read; **SNIPPET** — only search-result or index metadata was seen. A WebFetch summary never counted as FETCHED. Every quoted span in `evidence.jsonl` was re-verified in the main thread as an exact substring of the saved file; seven apparent mismatches were chased down and all seven proved to be bookkeeping artefacts (filename/id drift, stripped `//!` doc-comment prefixes, a README inside a subdirectory), not fabrication.

Three deviations from the run rules, declared rather than hidden. First, the output shape follows the run's own specification — SOURCES table, per-question findings, gaps — so the pipeline's default sections are absent by instruction. Second, C2 carries fifteen sources against a soft cap of about ten; the overrun is entirely the mandated "cited by" check on the founding papers, which produced the two strongest results in the question. Third, no design recommendations appear anywhere below.

Gate results, stated so they are not mistaken for a clean pass. `validate_artifacts.py` passes with zero violations and one warning, adjudicated below. `verify_citations.py` passes: 13 DOIs resolved against Crossref and 33 further URLs reachable, with four heuristic false positives (two pre-2000 papers flagged for "modern AI terms", one subtitle mismatch against Crossref's short title, one short tool-manual title) and two NYT URLs that return 403 to the checker exactly as they did to every other HTTP client in this run. Five DOIs were additionally resolved by hand against Crossref and all five returned the expected paper. `validate_report.py` **fails** with two errors, both naming the same absent sections — Executive Summary, Introduction, Main Analysis, Synthesis, Recommendations. That failure is the override in the paragraph above, not a defect, and it is reported here rather than worked around by inventing sections the brief excluded. A Phase 6 critique pass was run and its fifteen findings, including the three carried as `wontfix`, are in `critique.jsonl`; two of them changed the findings text materially and are noted where they apply.

The one open gate warning concerns the claim that ResearchGate returned HTTP 403. That claim is already scoped to the client used and says explicitly that nothing here establishes what the source holds, so it correctly carries no inaccessibility flag; the warning is the keyword backstop firing on the vocabulary, and it is adjudicated here rather than dodged by rewording.

## C1 — Constructor practice for theme-entry placement

### The hard rules, from the publisher

The only first-hand publisher specification retrieved is The New York Times's own submission page, dated 20 July 2026 and read in a browser session [12]. It lists five hard rules, described as "broken with extreme rarity": black square symmetry, all-over interlock, no unchecked squares, all answers at least three letters, and black squares used in moderation. Two details in that wording matter for anyone encoding the rule set. The symmetry rule is stated as black *square* symmetry "which typically comes in the form of 180-degree rotational symmetry" — 180-degree rotation is named as the usual instance of a broader requirement, not as the sole permitted symmetry, and the same qualification appears in the NYT's own construction walkthrough [11]. And the word-count ceilings are 78 for a 15×15, 72 for a themeless 15×15, and 140 for a 21×21, with the page adding that maximums may be exceeded slightly at the editor's discretion if the theme warrants. The page names only 15×15 and 21×21 as NYT sizes, in both its word-count table and its payment table; no 11×11 appears anywhere in the specification.

Cruciverb's Basic Rules page [1], which the page itself attributes to the NYT crossword editor, states the theme-symmetry consequence with a worked example: a major theme entry three rows down from the top requires another theme entry three rows up from the bottom. Matt Gaffney's account of professional practice [7] gives the same rule operationally — theme entries need to be symmetrical in length so they offset each other — with one exception, an entry running through the exact centre, which is symmetric with itself. Matt Dodge's novice write-up [9] is the clearest illustration of what the rule costs: four of his theme entries paired at 10 and 9 letters, but a fifth 13-letter entry had no length partner, so it had to be centred rather than dropped, and centring a 13-letter entry in a 15-column grid mechanically forced one black square at each end of that row. Nancy Salomon's theme-entry page [5] closes the obvious escape route: asymmetrical theme-related short entries are conventionally unwelcome, so an unpaired extra is rejected rather than tolerated.

### Row choice and spacing are convention, not rule

Every source that names row 3 frames it as usual practice. CommuniCrossings [6] states that the first theme entry usually appears in the third row of a 15×15, or the fourth row if it is 12 to 14 letters long. Cruciverb's Basic Rules [1] uses row 3 and row 13 only as an arithmetic illustration of the symmetry constraint, not as a placement mandate — any row works provided its mirror also carries a theme entry. Salomon's 21×21 advice [4] shows the same convention rescaled: she describes routinely running theme entries across rows 3 and 19 of a 21-row grid, 19 being the rotational mirror of row 3.

The NYT walkthrough [11] supplies the reason the convention exists, and it is a fillability argument rather than an aesthetic one: constructors place theme answers as far from one another as possible, which usually puts the first one in row 3. The same passage then shows the convention being overridden in the very example that introduces it — putting the 11-letter themer in row 3 would leave a band of three-letter words, and since there are far fewer three-letter than four-letter words, the constructors moved a different, shorter entry there instead. No source retrieved gave a fixed numeric row-gap rule. Spacing is governed indirectly, through the theme-square budget (Salomon gives a 15×15 norm of three or four entries totalling roughly 40–45 squares, and a 21×21 minimum near 80 [5]) and through the word-count ceiling, not through a stated number of rows between theme rows.

Theme entries may cross, and every source that mentions crossing discourages it on fill grounds. Salomon is blunt that beginners assume crossing theme entries makes life easier when in general the fill gets tougher [4]; she separately warns against long fill entries crossing three theme squares and against non-theme entries overlapping a theme entry by more than five squares, framing both as rules of thumb rather than limits. CommuniCrossings reports the same practice from the placement side, minimising multiple theme crossings to preserve fill options [6].

### Black-square layout around long entries

Roy Leban's Cruciverb page [2] is the most procedural source retrieved. Its method is forced-then-aesthetic: lay the theme entries first, place the blocks their endpoints force plus any blocks those in turn force — his worked example is a 10-letter entry starting at row 3, column 1, which forces a block at row 3 column 11 and, by symmetry and minimum-length propagation, blocks at column 11 of rows 1 and 2 — and only then shape the interior. The same page reports that most 15×15 grids resolve into roughly nine sections joined by two or three longer connector words, prefers diagonal block runs to straight horizontal or vertical runs because they fill more easily, treats "cheater" squares (blocks that do not change the word count) as something to introduce only when the fill genuinely needs them, and advises against a block in the central square most of the time.

Leban's page also warns against small isolated sections of words reachable by only "one way in", and states plainly that all rules including symmetry can be violated but that the more significant the rule, the better the reason needs to be [2].

The letter-level placement rules are the most directly transferable statements found in C1, and they are the one place where two independent sources agree in detail. Both [2] and [11] say that when a theme entry contains a hard consonant, the block should be positioned so that the crossing word *begins* with that letter rather than ending with it. Leban quantifies it for J: roughly half of all words containing a J start with it, and more than a hundred times as many words start with J as end with one [2]. The NYT article gives the same rule with JACOB as its example, generalising the reasoning to consonants doing double duty [11]. Leban then adds a letter-specific exception — an X is better placed in the middle of an entry than at either end [2] — and the NYT article adds an orthogonal rule about position in the *grid* rather than in the entry: hard letters in a theme entry are better tucked toward the edges than centred, because a central J, Q or Z interacts with more other theme material [11]. A third rule, again from [11], governs which letter of a placed entry to block after, deciding it on letter-position frequency in the word list: blocking after the N of NUMBER beats blocking after the U, because far more words end in N than in U. The same article documents that long non-theme "bonus" entries are conventionally placed Down rather than Across, so solvers do not mistake them for theme material, and that diagonal "stair step" block runs are the standard device for closing off a corner.

### Word-count and block-count ceilings

These are hard per-publication limits and they differ by outlet and by editor. Only the NYT figures were obtained first-hand [12]. CommuniCrossings [6] quotes the LAT, WSJ and Universal specification sheets as well — LAT max 78 with under 43 black squares preferred, WSJ max 78 and 140 (occasionally 144) for 21×21, Universal max 80 themed and 74 themeless with 146 for 21×21 and no fixed block maximum — but that is a secondhand transcription of those specs, not a retrieval of them, and should be treated as such. Salomon [4] gives editor-specific 21×21 maxima current at time of writing: Stan Newman 146, most other editors 144, Mel Rosen 142, Will Shortz and Susan West 140. That spread is the substantive point: there is no single industry word-count limit, and the applicable number is a property of the target editor. Below the hard cap, Salomon [3] gives a softer sales-oriented convention of 76–78 words for a themed 15×15. No source gave a hard block-count ceiling for a 15×15; Cruciverb notes the older roughly-16%-of-grid norm as no longer strictly enforced [1], and the constraint operates through the word count and the "moderation" language instead. The NYT walkthrough independently reports the 15×15 ceiling as 78 words and 42 blocks as displayed in CrossFire's summary panel [11].

### Two named targets that did not hold up

The run brief listed XWord Info as a confirmed source for placement practice. It is not one. Its constructor-facing pages are tool and statistics documentation: the FAQ retrieved [8] defines word count, cheater squares and open squares and states the NYT 78-word ceiling, and the Tour pages document the site's Finder and Analyze features. No theme-placement or grid-design tutorial exists on the site. Crossword Fiend was likewise checked directly [10]: its only post tagged for crossword construction is a 2018 mentoring-directory announcement, and the site's substance is daily-puzzle review and solver ratings, not construction technique. Cruciverb, listed as unverified in the brief, was verified — five of its pages were retrieved cleanly with no login [1][2][3][4][5].

## C2 — Fillability estimation without a full search

### The named phase-transition result, confirmed

Anbulagan and Botea 2008 is exactly as the brief named it: "Crossword Puzzles as a Constraint Problem", CP 2008, LNCS 5202, pages 550–554, DOI 10.1007/978-3-540-85958-1_40 [13]. The Springer version of record is closed on OpenAlex, and the only free route found is the authors' own ANU/NICTA page, from which the full text was retrieved. Its contribution is a phase-transition study of *realistic* rather than randomly generated grids, drawn from the Beacham et al. benchmark suite [19]. Varying dictionary size on 9×9 grids by adding 1% of the word list (2,200 words) at a time — the paper elsewhere names the benchmark dictionary as 220,000 words — hard instances occur between roughly 10,000 and 35,000 words; the hard band widens with grid size, running about 22,000–66,000 words at 15×15 and 22,000–110,000 at 23×23. Varying the number of blocked cells instead, on 23×23 grids at three dictionary sizes, produces the same three-region structure — an unsatisfiable region with few blocked cells, a hard region, and an easy satisfiable region with many — and the hard region went unsolved within a 24-hour limit in every case tested. The paper's practical import for a fixed grid size is that *block count and dictionary size jointly* determine which of the three regions an instance lands in.

### A closed-form solution-count estimate, and its honest limit

The strongest result in C2 came from the mandated cited-by check rather than from direct search. Botea and Anbulagan's follow-up, "Analysing the Behaviour of Crossword Puzzles" (SoCS 2009) [14], introduces a model-counting formula for the crossword domain and connects it to hardness. Their expected solution count is E(N) = N_a · p_i · p_r, where N_a is the total number of slot assignments, computed as the product over word lengths of m_l^{n_l} with m_l the number of dictionary words of length l and n_l the number of slots of that length; p_r is the probability that no word repeats, in closed form from the same two histograms; and p_i is the probability that all intersection constraints hold. Every ingredient except p_i is computable directly from the grid geometry and the word list's length histogram, with no search. They then invoke the Williams–Hogg identity — that in soluble instances the effort to find a first solution can be estimated as the effort to exhaust the search space divided by the number of solutions — to turn a solution-count estimate into a hardness prediction.

The caveat is theirs and it is explicit. Their first estimate of p_i was 26^{-c} for c intersection cells, from assuming uniform letter distribution and independence across intersections; in practice this "turned out to be quite inaccurate", which they attribute to English letter frequencies being far from uniform. They fall back to fitting p_i empirically against exactly-counted small instances (they obtain 1/17.5 on 6×6 grids) and state that finding a better estimation formula for p_i remains an open issue. So the published state of the art on estimating a crossword's solution count leaves the intersection factor as a calibrated constant, not a computed one.

### The generic CSP framing, verified from primary sources

Both canonical papers were read in full rather than recalled. Gent, MacIntyre, Prosser and Walsh's "The Constrainedness of Search" (AAAI-96) [15] defines κ = 1 − log₂⟨Sol⟩ / N, with N the number of binary state variables and ⟨Sol⟩ the expected number of solutions across an ensemble, and locates the soluble/insoluble transition near κ ≈ 1. The load-bearing caveat is in the paper itself: κ is a property of an *ensemble* defined by a generation method, not of a single instance. Cheeseman, Kanefsky and Taylor's "Where the Really Hard Problems Are" (IJCAI-91) [16] is the earlier order-parameter result both papers descend from; it establishes that NP-complete classes admit at least one order parameter whose critical value separates an over-constrained mostly-insoluble region from an under-constrained mostly-soluble one, and explains the cost peak at that value by the high density of well-separated near-solutions there. Neither is crossword-specific; the crossword instantiation of the framework is [13] and [14].

### The empirical result that bears most directly on cheap estimation

Ginsberg, Frank, Halpin and Torrance's "Search Lessons Learned from Crossword Puzzles" (AAAI-90) [18] is explicitly a construction paper — it builds a program that generates crossword puzzles — and it was recovered free from AAAI's own CDN after the bibliographic indexes reported it closed. It draws the distinction C2 is asking about with unusual clarity. The *cheapest-first* heuristic constructs a statistical estimate of the number of choices remaining for each slot at compile time and orders slots by that estimate; *dynamic search rearrangement* instead counts the actual remaining possibilities at run time. Their conclusion 2 is that ordering variables at run time is far more efficient than using the compile-time statistical estimate, and their data show the two hardest of their four puzzles unsolvable within a twenty-minute limit unless run-time information was used. This is direct empirical evidence against the cheap-statistical-proxy family, from the same paper that supplies the least-constraining-value rule: for each of the first k candidate words for a slot, compute the number of remaining possibilities for each unfilled crossing word and take the product; choose the word maximising it. They set k (called min-look) to 10, on the argument that the time spent examining further candidates is not repaid, and report that this value-ordering work only pays off on grids of 9×9 and larger.

Meehan and Gray 1997 [17] formalise the complementary most-constrained-slot rule — instantiate the slot with the fewest matching dictionary words first — and are candid that the fail-first argument behind it assumes slot independence, which crosswords violate by construction, so the heuristic is empirically useful rather than justified. Beacham, Chen, Sillito and van Beek 2001 [19] is the origin of the realistic benchmark suite [13] reuses, and its finding is a methodological warning: model, algorithm and heuristic choices interact, so none can be optimised independently.

### Propagation as a proxy: where it is a certificate and where it is not

No paper was found that runs a cheap propagation pass specifically to predict crossword fillability. What was found is the theoretical boundary. Cohen, Carbonnel, Živný and Cooper (STACS 2018) [20] show that singleton arc consistency is a *complete* decision procedure — not merely a filter — for CSPs over constraint languages of bounded width, and characterise this by five forbidden binary micro-structure patterns. Crossword word-compatibility relations are arbitrary same-length dictionary subsets and are not expected to fall in those classes, so on a crossword region propagation retains only its one-sided guarantee: a domain wipeout proves unsatisfiability, while a domain surviving propagation certifies nothing. Gourvès, Harutyunyan, Lampis and Melissinos [23] supply the complementary negative from complexity theory: filling crosswords remains NP-hard under extremely severe structural restrictions on the intersection graph — a union of stars with a two-letter alphabet, or a matching with a three-letter alphabet — and the treewidth-parameterised m^tw algorithm cannot be improved to fixed-parameter tractability under ETH. That is evidence against the general adequacy of cheap *structural* proxies, independent of any particular heuristic.

### Learned proxies, and a measured comparison against a hand-made one

Two lines address predicting cost or quality from features without running the search. Leyton-Brown, Nudelman and Shoham [22] and Hutter, Xu, Hoos and Leyton-Brown [21] give the general empirical-hardness-model methodology: fit a supervised model from cheaply computable instance features to predicted runtime, then read the fitted model to see which features drive hardness. Neither is crossword-specific. The transfer is that a crossword instance exposes exactly the class of features these models consume — grid geometry, per-slot candidate counts, domain sizes after propagation, dictionary composition — and the methodology is defined over such features rather than over any particular domain; nothing in either paper instantiates it for crosswords.

The crossword instantiation exists elsewhere and was reached through the cited-by chain. Bulitko and Botea (CoG 2021) [26] train a convolutional network whose only input is a 13×13×1 matrix of the black-cell pattern — black cells encoded +0.5, empty −0.5, with no word-list or partial-fill features at all — to regress the score their filler would achieve, and use it as a fast proxy fitness function. On 100 held-out grids the Spearman rank correlation between the network's prediction and the filler's actual score is −0.64, against −0.24 for the obvious hand-made baseline of maximum word-slot length. That contrast is the useful number: a learned function of the block pattern alone tracked achievable fill quality roughly two and a half times better by rank correlation than the single most obvious geometric statistic. The constraint set is Romanian competition rules — at most 26 black cells on a 13×13, no rotational symmetry requirement, slots of length 1 and 2 permitted — so the result does not carry to American grids unmodified.

Botea and Bulitko's AIIDE 2022 paper [25] states the standard construction model precisely — variables are slots, a slot's domain is the set of words that fit it, and propagation shrinks the domains of uninstantiated slots as words are placed — and introduces tiered state expansion, which splits a slot's domain into a small likely-good tier and a deferred tier, by which time propagation has already shrunk the deferred set. Their SoCS 2021 paper [30] is the one that deliberately runs a search expected to fail, with the target score set unreachably high so pruning is aggressive, and keeps the best partial grid reached as the seed for a second search at an achievable target; the premise is that a failed, heavily pruned search still localises where a good solution lies.

### Density measures, and the explicit negative

Dakowski, Wojna and Jaworski (CoG 2022) [27] publish the only explicit numeric density objective found for crossword grids: f(x) = intersections(x) · letters(x) / (width(x) · height(x)), the count of crossings times the letter density of the bounding box, with a reported mean intersections-to-letters ratio of 13.95% for their better algorithm. They are equally explicit that both their algorithms produce puzzles humans cannot solve in reasonable time, so maximising that objective is not a proxy for a good puzzle. Agarwal and Joshi [24] offer greedy per-move fitting scores and backtracking triggers for grids whose geometry is not fixed in advance, rather than an upfront region-fillability estimate.

Searched and not found: any formal constraint-density or "openness" metric defined specifically for crossword grids — crossing-to-cell ratio, average slot degree, or similar — beyond the generic CSP notion of constraint density and the treewidth framing in [23]; and any paper predicting the solvability of a partial crossword *region* as opposed to a whole instance. Searches for singleton arc consistency, shaving, bounds-consistency failure and limited-discrepancy search used as pre-search fillability predictors returned only the general CSP literature with no crossword tie-in.

## C3 — Grid-layout generation given fixed theme entries

### The founding paper does not address the question

Mazlack 1976 is confirmed as "Computer construction of crossword puzzles using precedence relationships", *Artificial Intelligence* 7(1), pages 1–19, DOI 10.1016/0004-3702(76)90019-9 [28]. Its full text is behind purchase or institutional sign-in and no preprint exists in any repository searched. The abstract, however, was read in a browser session after HTTP clients were refused, and it settles the relevance question directly: the paper reports a crossword generator that, after whole-word insertion failed, succeeded with a letter-by-letter method requiring a dynamic heuristically determined decision structure, and it names its subject matter as letter selection, ordering and reordering of the solution sequence, dictionary structure and access, and decision-path selection. Black squares, symmetry and pre-placed entries appear nowhere in it. The named founding paper of this question is a fill-order paper, and the one secondary characterisation available — Botea's one-line summary that Mazlack fills a grid letter by letter [29] — agrees.

Its cited-by list was checked on three services, which disagree on count: ScienceDirect's own counter shows 17, OpenAlex 18, Semantic Scholar 26. The construction-side descendants are [18], [19], [13], [14], [30], [25], [32], [34], [35] and [33]; the remainder are solving systems (WebCrow, Proverb, Dr.Fill, diagramless solvers) and are out of scope. None of the descendants proposes black-square layouts given fixed entries.

### The pattern across the whole academic line: the block pattern is an input

The consistent finding of C3 is that from Mazlack forward, the blocked-cell pattern is supplied to the algorithm rather than chosen by it. Botea 2007 states it as a constraint of the problem definition — no blocked cells can be added or removed during the process [29]. blacksquare [37] implements a symmetry enum with automatic mirroring of a manually placed black square and a post-hoc validator, but its generative core is an autofill over an already-fixed pattern. Rigutini et al.'s systems are characterised in the citing literature as satisfying a black-field pattern that comes from a random generator [34][35][27].

Two papers by the same pair of authors in the same year appear to contradict each other on this, and the contradiction resolves cleanly. Botea and Bulitko's SoCS 2021 paper [30] restricts itself to the word-adding half of a task that nominally requires adding both black cells and words, and lists generating good configurations of black cells as future work. Bulitko and Botea's CoG 2021 paper [26] does precisely that: a genetic algorithm mutating black-cell positions — each mutation shifting one black cell to a neighbouring empty cell — under an explicit constraint set of no two black cells cardinally adjacent and full connectivity of the empty region, with the CNN proxy described under C2 as the fitness function. It reports that the proxy-guided evolution was the only method tested that produced grids the filler could complete. So black-cell layout generation is *not* open in that literature; it is solved under Romanian competition rules, which include neither 180-degree rotational symmetry nor a minimum entry length of three.

### Where layout generation under something like American constraints does exist

Engel, Holzer, Ruepp and Sehnke 2012 [31] generate black-square masks with a genetic and a memetic algorithm under formal 4- and 8-connectivity constraints, and prove mask generation NP-complete. The style is Swedish, which carries no rotational-symmetry requirement, so the connectivity formalism and the complexity result transfer while the symmetry half of the problem is simply absent from their model.

Two open-source projects place black squares from fixed entries. katahiromz/XWordGiver [39] (MIT, C++, created 2019, last commit 2026-07-02) implements `from_words_t::apply_candidate()` in `crossword_generation.hpp`, which places a required word and immediately writes black squares at both ends along its axis, tracked against a selectable `RULES::POINTSYMMETRY` flag for 180-degree symmetry. This is genuine fixed-entry-driven block placement with an American-compatible symmetry option, but the project's own README says it is optimised for Japanese crossword generation and that Latin-alphabet patterns may be improper. jgotangco/PuzzlePlot [38] (MIT, JavaScript, last commit 2026-08-30) implements `autoGenerateCrossword({rawInputWords, size, symmetry})` in `js/engine/crosswordUtils.js` with a stated guarantee of symmetrical layout, single connected region, minimum length three and zero unchecked cells — the closest literal match found to the question as posed, verified by reading the generator source, but unpublished hobby code with no algorithmic analysis and no adoption. On the academic side the nearest match is Agarwal and Joshi [24], whose stated problem is determining both word locations and grid geometry from a fixed vocabulary, but whose text contains no mention of symmetry at all.

The accurate summary is therefore not "nobody does this". It is that the peer-reviewed American-style construction literature does not address black-square layout given fixed theme entries under the full constraint bundle — symmetry, connectivity and minimum length simultaneously — while working code that does exists in small, unreviewed projects, and closely adjacent published work solves the problem with one of the three constraints dropped.

### Counting valid grid patterns

The enumeration sub-question produced the only exact numbers in this run. Ferry [42] computed, by dynamic programming, that there are 404,139,015,237,875 connected, 180-degree-symmetric, minimum-length-3 grids in which the white region touches every edge, and 409,764,131,469,788 without that last requirement — originally posed as a FiveThirtyEight *Riddler* problem. Balgord [41] brute-force-enumerated all valid 5×5 grids by symmetry type: 12 under 180-degree rotation, 2 under 90-degree rotation, 6 horizontal, 6 vertical and 26 diagonal. Coté and Merrill [40] give the graph-theoretic formalisation intended to generalise these counts, defining a class of multigraphs whose necessary conditions correspond to the five American structure rules — connectivity, 180-degree symmetry, minimum length three, full keying, no fully void row or column — but leave the counting step itself as a next phase and cite Ferry's figure as their target.

One cited-by descendant sits adjacent rather than inside this question. Niculescu and Ştefănică [32] generate *perfect* grids, meaning grids with no black cells at all, so black-square layout does not arise; the transferable content is representational — one trie per word length, each node carrying a 26-bit code recording which letters may follow, so an intersection can be tested by a bitwise AND rather than a dictionary lookup, with intersection data precomputed into matrices.

## C4 — How tools score a placement

### The distinction that governs the answer

Three mechanism families were found, and the one the question names is the one that barely exists. Tools rank **which slot to fill next**, and they rank **which word to put in a given slot**. Almost none rank **where in the grid a given entry should go**. The author of Ingrid answers this directly in his own FAQ: placing black squares and theme entries is still a manual process, and he is not aware of any construction tool that automates it [45]. The single confirmed exception found is Crossword Compiler's "Fit theme words" feature [49], which scans grid patterns for places a short list of theme words will fit and lets the constructor choose among the arrangements — an enumeration, not a scored ranking.

CrossFire's "Best Location" is confirmed to exist and confirmed *not* to be an entry-placement ranker. Its manual [43] describes it as having the filler choose a constrained word which will give the most "bang for the buck" in filling — a slot-ordering feature. CrossFire's visible scoring inputs are a dictionary Word Score; a per-word Grid Score described as the quality of the neighbourhood immediately around the word, with values above 0.9 considered good; a Final Score for a completed fill; and a separate XScore that ranks already-placed words by crossing quality so the constructor can spot trouble.

### Slot ordering

Crossword Compiler's Pro Grid Filler [49] documents the same family in its own words: the program automatically suggests which word slot to fill next, with an option to let it determine where it thinks the best place to start is. Exet [47] ranks unfilled slots by how few viable fill suggestions remain and provides a `!` key to jump to the most constrained. Qxw [51] presents a feasible-character list at the cursor ordered from most to least promising, plus hotspot dots for slot-level triage, though its manual documents no single-button jump command. The most precisely specified instance is Ingrid's open-source core, ingrid_core [46] (MIT, Rust, actively maintained through 2026-07), whose `src/backtracking_search.rs` states in its own module documentation that it maintains arc consistency with AC-3 and orders variables with a variant of the `dom/wdeg` heuristic; the slot priority is computed as `remaining_option_count / slot_weight`, lower winning, with the weight accruing from domain-wipeout history. That is a fully specified, readable implementation of the same idea CrossFire exposes as a button.

### Word ranking within a slot

CrossHatch [44] (MIT, TypeScript, last commit 2021) is the most transparent: `src/lib/entryCandidates.ts` scores a candidate as `(crossScore + minCrossScore) * wordScore * (100 if not iffy else 1)`, where the cross scores come from simulating letter-matrix propagation across the slot's open crossings and summing the dictionary scores of the surviving cross-candidates. Ingrid's app documents its "Recommended" sort as balancing word score, letter score and a factor based on how many options will be available in the crossing slots, and its FAQ is explicit that this is not based on full-grid fill quality [45]. Crossword Compiler sorts words by how good they are and offers a non-stop filling mode that ranks complete fills by score [49]. Crosserville sorts slot options by word score, higher first [52].

### The negative results

Phil [48] (Apache-2.0, JavaScript, last commit 2025-01-02) has no candidate-ranking or position-scoring feature at all. Its fill engine is SAT-based, using Glucose 3.0, which returns one satisfying assignment rather than a ranked list; grepping its fill-logic source `cross.js` for score, rank, candidate, heatmap and best returned zero matches. Its README now directs users to a proprietary iOS successor. Exet [47] is a cryptic-oriented tool — its default word lists are general English lexicons scored by Wikipedia occurrence, and its Research and clue tabs are cryptic-specific — but its README documents a first-class "New US-style doubly checked grid" mode and grid-completion logic that branches on the American all-cells-checked format versus the British chequered format, so its fill and ranking mechanics do transfer to American construction and only the clue tooling does not.

## C5 — Crossing-quality heatmaps and their banding

The clearest match to the feature described, with documented discrete banding, is **Crosserville** [52], found indirectly through Ingrid's FAQ. Its own FAQ states the thresholds: ten or fewer candidates highlights the slot yellow; exactly one candidate highlights it yellow and shows the sole candidate in grey; zero candidates highlights it red. More than ten gets no highlight, an implicit unmarked band. The same answer carries the caveat that these colours are computed from raw pattern-matching candidates rather than confirmed-valid options, so a counted candidate can still be a dead end. Crosserville separately offers per-slot letter-distribution bar charts, computed either from word-list scores or from live constraint-filtered matches — a different overlay showing letter frequency rather than word count.

**Exet** [47] implements the same idea with continuous rather than tiered banding, and the formula was read from source (`exet.js`, `updateViablots` and `viability`): zero candidates renders as purple at the largest radius; 1 to 15 candidates render red with radius shrinking as log₂(count) rises; 16 or more is fully transparent. **Qxw** [51] documents a closely analogous "hotspot" mechanism — red dots on cells with relatively few feasible letters, bigger dots meaning fewer possibilities, a distinct grey marker at exactly one remaining possibility and a grey question mark at zero — but gives no numeric thresholds for the size scaling in the manual, and its source is not published alongside it.

**CrossFire** [43] has a genuine numeric threshold, but on possible *letters* per cell rather than possible words per slot: a cell constrained to exactly one letter shows it in dark grey as a forced letter, a cell with 2 to 9 possible letters shows them in miniature inside the cell, and a cell with 10 or more shows nothing. Separately, its Quick Fill highlights entire dead-end regions in red (approximately, not per-cell) and pre-marks any grid word with zero candidate fills in pink — binary rather than graduated.

Two clean negatives. Crossword Compiler's Grid Insight [50] runs a background full-fill feasibility analysis but surfaces only a single binary green/red indicator for a whole grid section, with no per-cell or per-slot candidate-count overlay documented in any of the four pages fetched. CrossHatch's colour coding [44] is on *filled* cells and encodes the word-quality tier of the word actually placed, not the candidate count of an unfilled slot — and its README describes three tiers (Good ≥50, Okay 40–49, Iffy) while `Square.tsx` implements a five-value enum (Lively, Normal, Crosswordese, Iffy, NotAThing), a documentation-to-code mismatch worth knowing before trusting the README. Phil and the Ingrid app document no candidate-count overlay at all; Ingrid's nearest analogue is a shaded slot edge indicating an extra constraint (approved or rejected words, a pinned filter, an overridden score), confirmed by tooltip rather than by colour gradation.

One adjacent artefact is worth recording because it is often mistaken for this feature. The NYT walkthrough [11] reproduces a heat map by Darren McCleary showing how black-square density varies by day of the week — Mondays closed off with many edge blocks, Saturdays wide open. It is a heat map over published grids' block patterns, not a per-cell candidate-count display, and it says nothing about remaining fill options.

## Gaps and Limitations

**Not obtained.** Mazlack 1976's full text [28]; only the abstract was read. It is behind purchase or institutional sign-in at Elsevier, and no preprint was found on OpenAlex, Semantic Scholar, Crossref, CiteSeerX, arXiv, the Wayback Machine or any university repository searched. Four cited-by descendants remain at SNIPPET with no free copy located: Bonomo, Lauf and Yampolskiy 2015 [33], Rigutini et al. 2012 [34] and 2008 [35], and Harris 1990 [36].

**Cited-by not run.** Meehan and Gray 1997 [17] has no OpenAlex record — an exact-title query returns zero results — and the keyless Semantic Scholar endpoint returned HTTP 429 on the attempt, so no descendant list could be built for it. This is the one founding-paper cited-by check the run rules require that was not completed.

**Searched and not found.** No IJCAI companion paper by Mazlack; this rests on web search, not on a direct search of the free ijcai.org proceedings archive, so it is an unconfirmed absence rather than a verified one. No formal constraint-density or openness metric defined specifically for crossword grids. No paper predicting the solvability of a partial crossword *region*. No literature applying singleton arc consistency, shaving, bounds-consistency failure or limited-discrepancy search as a crossword fillability predictor. No free excerpt or sample chapter of Patrick Berry's *Crossword Constructor's Handbook* was found by search; a Cruciverb support thread about the book concerns purchase and download problems, not content. No construction-methodology documentation on crosswordnexus.com itself, and no freely accessible essay by Erik Agard or Brooke Husic laying out concrete placement rules — only interviews and a paid course listing.

**Deliberately not pursued, and why.** Crosshare, Crossworthy, Cruciform and Squared were dropped against the C4 source cap once the six named tools plus Qxw and Crosserville were covered; "Cruciform" returned no distinct construction product. Ferland's crossword-counting papers, cited inside [40], were left once [41] and [42] had produced concrete numbers. Forster, Harris and Smith's 1992 "The Crozzle — a problem for automation" (ACM, gold OA) surfaced while chasing [36] and was not pursued: the Crozzle is a different puzzle with a different objective, and assessing the transfer would have cost more than the cap allowed. Several GitHub repositories were triaged and dropped: janeymunoz/crossword_generator generates NYT-valid symmetric grids but not from a required word list; njones167/xgrid and daniel-d611/xword-grid-lint report violations rather than generating layouts.

**Known weak points in what is reported.** The LAT, WSJ and Universal word-count and block figures are a secondhand transcription via CommuniCrossings [6]; only the NYT numbers were retrieved from the publisher [12]. Salomon's editor-specific 21×21 maxima [4] are undated and may have drifted. Beacham et al. [19] was fetched but its PDF has broken font encoding, so no machine-verified verbatim quote could be taken from it. Qxw's implementation language is not stated in its manual. Ingrid's app internals are visible only through its FAQ; only its Rust core is open. Two of the three C3 code projects matching the constraint bundle are hobby repositories with negligible adoption, and their behaviour was verified by reading source, not by running it.

### Retrieval Access

Three sources returned results to HTTP clients that would have been wrong to report as findings, and were re-tested in a real browser session:

- **nytimes.com** — every crossword-construction URL tried returned a 771-byte body containing a DataDome bot-challenge script, to `curl` with a Chrome User-Agent, to WebFetch, to the r.jina.ai proxy and to the Wayback Machine. In a Chrome session both target pages rendered in full [11][12]. The block was a client wall; the source is not closed.
- **mdpi.com** — the article and PDF URLs, and the DOI redirect, all returned HTTP 403 with a ~400-byte Akamai "Access Denied" body. In a Chrome session the full gold-OA article rendered [32]. Again a client wall, not a closed source.
- **sciencedirect.com** — returned HTTP 403 with a 1.2 MB Elsevier bot-challenge page to a browser User-Agent. In a Chrome session the abstract, reference list and citing-articles list rendered; the *full text* is genuinely behind purchase or institutional sign-in, which is a property of the source and is backed by that browser observation [28].

Two further blocks were observed by HTTP only and are scoped accordingly: **researchgate.net** returned HTTP 403 with a 21-kilobyte body to a browser User-Agent, and **CiteSeerX**'s viewdoc endpoint 301-redirects to a Wayback capture which returned HTTP 429 with a bot-traffic message. Neither was tested in a browser, so nothing here establishes what those sources hold; the ResearchGate target [17] was obtained from a free mirror instead, and the CiteSeerX target [18] was obtained from AAAI's own CDN.

Paired `access_observation` rows for each of the three browser-tested cases are in `evidence.jsonl`, recording both the HTTP probe and the browser result with their true `access_mode`.
